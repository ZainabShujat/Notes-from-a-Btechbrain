Introduction to AI Agents

1. Introduction

Most people first meet AI as a box that answers questions. An AI agent is different: you hand it a goal, and it works toward that goal by looking at its situation, deciding what to do, using tools, and checking what happened. This is why agents are behind coding assistants that fix failing tests and research tools that gather sources for you.

This module gives you the mental model for the whole course. By the end you will be able to define an agent precisely, describe its loop and components, tell agents apart from chatbots, automations and workflows, and, just as important, decide when not to build one.

2. What Is an AI Agent?

An AI agent is a system that pursues a goal by repeatedly observing its environment, deciding on actions, and acting, using the results of each action to decide what to do next. Six ideas make that definition work:

  • Goal-driven behavior: the agent is given an outcome ("find the cause of this bug"), not a script.
  • Perception: it receives inputs: user messages, files, API responses, error logs.
  • Reasoning: it interprets those inputs and decides what matters.
  • Planning: it chooses a sequence of steps, and revises it when things change.
  • Action: it does something that affects the world: runs a search, edits a file, sends a request.
  • Observation/feedback: it reads the result of that action and uses it in the next decision.
Practical example. You ask: "Why is our checkout page slow?" An agent might read the performance logs (observe), suspect a slow database query (reason), plan to inspect queries then check indexes (plan), run a query-analysis tool (act), see that one query scans a whole table (observe), and then propose an index. Each step depended on the last result. Nobody wrote that exact sequence in advance.

3. AI Model vs AI Application vs AI Agent

ExampleA hosted language modelAn email app with "summarize this thread"An assistant that triages your inbox and books meetings

Calling an LLM API does not make something an agent. A "summarize this text" button makes one model call and shows the result. There is no goal to pursue, no choice of action, and no feedback loop. It is an AI application, and that is perfectly fine: often it is the right design.

4. How an AI Agent Works

Every agent runs some version of the same loop. It starts with a goal, then repeats until the goal is met or a stop condition (step limit, budget, or "I need a human") is reached.

In practice "Reason" and "Plan" are often one model call. The key is the arrow that comes back: the result of an action changes the next decision.

5. Anatomy of an AI Agent

  • Model: the reasoning engine that decides the next step.
  • Instructions: role, rules, and boundaries ("never delete data").
  • Tools: functions the agent can call; they are its hands.
  • Memory: short-term (this run) and long-term (across runs).
  • Context: everything placed in front of the model on a given step. It is limited, so what you include matters.
  • Planning: how work is broken into steps and revised.
  • Environment: the world the agent acts on.
  • Output/action layer: executes tool calls, validates them, and returns the final answer.

7. LLM-Powered Agents

Agents existed long before LLMs, but they needed hand-coded rules for every situation. LLMs changed that by making these things practical:

  • Reasoning: the model can interpret messy, unexpected input.
  • Natural-language goals: you write "summarize last week's incidents" instead of a formal spec.
  • Tool selection: given tool descriptions, the model picks which to call.
  • Dynamic planning: it can change course after an error.
  • Structured outputs: the model can return JSON matching a schema, so code can act on its decision reliably.
  • Tool calling: the API returns a request like {"tool":"search","args":{"query":"..."}}; your code runs it and sends back the result.
Example. A travel agent gets "Find me a cheap Friday flight to Pune." The model calls search_flights(date="Fri", dest="PNQ"), sees no results under budget, then decides to try nearby dates, a different tool call, and finally reports the cheapest option with a caveat.
Trade-off: the flexibility comes with non-determinism. The model can pick the wrong tool or loop. Guardrails, step limits, and validation are part of the design, not extras.

8. AI Agent vs Chatbot

A chatbot can be excellent at conversation without taking any action. An agent is defined by acting and adapting, not by chatting. Many agents have a chat interface, but the interface is not what makes them agents.

9. AI Agent vs Traditional Automation

Deterministic automation follows rules: "when a file lands in this folder, upload it." Workflow automation chains steps, possibly including model calls. Agents decide the steps themselves. If the rule is fully known, an agent only adds cost, latency, and a chance of mistakes. Renaming files by a fixed pattern needs a script, not a model.

10. AI Agent vs Workflow

A workflow has a fixed sequence written by you: extract → classify → draft → send. A model may power individual steps, but the order never changes. An agent chooses the order at runtime: it may search twice, skip a step, or retry with a different tool.

WorkflowAgent
ExecutionFixed sequenceAdaptive
PredictabilityHighLower
TestingTest each stepTest behaviors and outcomes
Choose whenSteps are known in advanceSteps depend on what is discovered

Example: "Turn each meeting recording into a summary and email it" is a workflow. "Investigate why this deployment failed and fix it" is agent territory. Many real systems mix both: a workflow with one agent step inside it.

12. When Should You Build an Agent?

Consider an agent when several of these are true:

  • The task has multiple steps, and the number is not fixed.
  • The environment is dynamic: data or systems change.
  • Decisions depend on intermediate results.
  • Tools must be chosen dynamically depending on the situation.
  • The task needs adaptation: retrying, replanning, handling surprises.

13. When Should You NOT Build an Agent?

  • A normal function is enough: converting currency, validating an email format.
  • Deterministic code is safer: payments, permissions, anything where a wrong "creative" step is costly.
  • A fixed workflow suffices: the steps never change.
  • The task is trivial: one model call, or none, solves it.
  • Latency or cost does not justify it: each loop iteration is another model call and more waiting.
Rule of thumb: use the simplest thing that works. Start with code, then add a model call, then a workflow, and reach for an agent only when the simpler options genuinely fall short.

14. Common Misconceptions

  • "Every LLM application is an agent." No. Without a goal-directed loop and action choices, it is an application using a model.
  • "Agents are autonomous humans." They are software following instructions within limits you set. They do not understand the world like people do.
  • "Agents always need multiple LLMs." One model in a loop is a complete agent.
  • "More agents means a better system." Extra agents add coordination cost, failure modes, and expense. Add one only when a role truly needs separating.
  • "An agent must continuously think." It reasons when a decision is needed. Many steps are plain tool execution.
  • "Agents eliminate software engineering." They increase it: you still design tools, validation, permissions, evaluation, and monitoring.

15. Practical Example: A Research Agent

User: "Research the latest developments in solid-state batteries and write a concise report."

  1. Understand: topic is solid-state batteries; output is a short report on recent developments.
  2. Plan: find recent news, company announcements, and technical sources.
  3. Select tools: web search and a page reader.
  4. Search and gather: run queries, open promising pages, extract key claims.
  5. Evaluate: prefer primary or reputable sources, flag conflicts, notice gaps and search again.
  6. Synthesize: group findings into themes.
  7. Report: write a concise, cited summary with uncertainties noted.

16. Code Example: A Minimal Tool Loop

def get_weather(city: str) -> str:
    return {"Pune": "31°C, sunny"}.get(city, "unknown")

TOOLS = {"get_weather": get_weather}

def run_agent(goal: str, llm, max_steps: int = 5) -> str:
    messages = [{"role": "user", "content": goal}]
    for _ in range(max_steps):              # stop condition
        reply = llm(messages, tools=list(TOOLS))   # model decides
        if reply.get("tool_call") is None:
            return reply["text"]            # goal complete
        call = reply["tool_call"]
        result = TOOLS[call["name"]](**call["args"])   # act
        messages.append({"role": "tool", "content": result})  # observe
    return "Stopped: step limit reached."

How it works. llm stands for any tool-calling model API. Each iteration sends the conversation so far. If the model asks for a tool, we run it and append the result, so the next decision sees it. If it answers directly, we finish. max_steps prevents endless loops. A production version adds argument validation, error handling, logging, and permission checks, but the core idea is exactly this loop.

17. Key Takeaways

  • An agent pursues a goal through a loop of observe, reason, plan, act, and observe again.
  • Calling an LLM is not enough; goal-directed loops, actions and feedback make an agent.
  • Core parts: model, instructions, tools, memory, context, planning, environment, action layer.
  • Chatbots answer; workflows follow fixed paths; agents choose paths at runtime.
  • Agents trade predictability, cost, and speed for flexibility.
  • Prefer the simplest design that solves the problem.

Agent Architecture

1. Why architecture matters

A model alone cannot search, remember, or act. An agent is a system around a model, and most failures (wrong tool, forgotten facts, endless loops) are system-design failures, not model failures. Click a component to see its job.

2. The model

The model is the decision-maker. Choose it by reasoning quality, latency, cost, and context window. A stronger model plans better but is slower and pricier; a smaller one suits simple routing steps. Model output is non-deterministic, so anything that must be exact (calculations, permissions) belongs in code.

3. Instructions

Instructions define role, constraints, tool guidance, output format, and safety rules ("never delete files; ask before spending money"). Be specific: vague instructions produce vague behavior.

4. Tools

A tool is a function the model may request, described by a name, description, and parameter schema. The model only requests a call; your code validates and runs it.

ToolExample argumentsReturns
web_searchqueryresult snippets
query_dbread-only SQLrows
calculatorexpressionnumber
run_codecode, timeoutstdout, errors
read_filepathfile text

5. Tool-calling flow

6. Memory, context, and state

  • Short-term memory: the conversation and tool results in the current run.
  • Long-term/external memory: facts stored in a database or vector store and retrieved when relevant.
  • Context: what the model sees on one step. It is limited, so include only what helps; summarise or drop the rest.
  • State: the agent's progress (current step, attempts, partial results). Without it, multi-step tasks restart or repeat.

Add memory only when the task needs it. A one-shot task needs none.

7. Planning and environment

Planning can be implicit (the model picks the next step each turn) or explicit (it writes a task list first, then revises). Every plan needs stopping conditions. The environment is everything the agent can observe and change: files, APIs, databases. Grant only what the task needs.

8. Practical example: a coding agent

9. Code: tool definitions and execution

TOOLS = {
  "read_file": {"fn": read_file, "params": {"path": str}},
  "run_tests": {"fn": run_tests, "params": {}},
}

def execute(call):
    tool = TOOLS.get(call["name"])
    if tool is None:
        return {"error": "unknown tool"}          # validate
    for k, t in tool["params"].items():
        if not isinstance(call["args"].get(k), t):
            return {"error": "bad argument: " + k}
    return {"result": tool["fn"](**call["args"])}  # execute

The model picks call; this code checks it against the schema, runs it, and returns either a result or an error the model can react to.

10. Common mistakes

  • Too many tools (the model picks badly) or unrestricted tools (unsafe).
  • Unclear instructions; no validation; no stop condition.
  • Stuffing excess context or adding unnecessary memory.
  • Treating the LLM as the whole system instead of one component.

Key takeaways

  • An agent is a model plus instructions, tools, memory, state, and an environment.
  • The model requests; your code validates and executes.
  • Keep context focused and permissions minimal.

Building Your First AI Agent

1. From LLM call to agent

2. Define the goal and the tools

Turn "help with my research" into an objective with a finish line: "Find three recent sources on X and write a 200-word summary with links." Then give each tool a clear contract: name, purpose, typed parameters, and what it returns on failure.

3. The tool-calling lifecycle and the loop

4. Stop conditions

ConditionWhy
Goal completedModel returns a final answer
Maximum stepsPrevents endless loops
Timeout / budgetBounds time and cost
Repeated failureSame error 2–3 times → stop
Human interventionRisky or unclear situations

5. Error handling and structured outputs

Treat errors as observations: return them to the model as text so it can retry with better arguments. Handle tool failure, invalid arguments, API outages, malformed output, and unexpected results separately. Schemas make outputs machine-checkable: parse, validate, and re-ask if invalid.

6. Memory and human-in-the-loop

For a first agent, the message list is your memory. Ask for approval before irreversible or costly actions (sending email, deleting, paying), not before every step.

7. Code walkthrough: a research assistant

def run(goal, llm, tools, max_steps=6):
    msgs, fails = [{"role": "user", "content": goal}], 0
    for step in range(max_steps):
        reply = llm(msgs, tools=list(tools))
        call = reply.get("tool_call")
        if not call:
            return reply["text"]                  # done
        out = execute(call)                       # validate + run
        fails = fails + 1 if "error" in out else 0
        if fails >= 3:
            return "Stopped: repeated failures."
        msgs.append({"role": "tool", "content": str(out)})
    return "Stopped: step limit."

It calls the model, runs any requested tool, feeds the result back, and stops on completion, failures, or the step limit.

8. Testing, debugging, production

  • Test tools like normal functions; test single steps with fixed model replies; run scenario tests and deliberate failure tests; evaluate final outputs against a checklist.
  • Debug by reading the full trace: wrong tool → improve descriptions; loops → tighten stop rules; hallucinated arguments → stricter schemas.
  • Production: log every step, retry transient errors, respect rate limits, enforce permissions, track cost, and add observability.

Key takeaways

  • An agent is an LLM in a bounded, validated tool loop.
  • Errors are inputs; stop conditions are mandatory.
  • Approve risky actions; trace everything.

Agentic Workflows

1. What is an agentic workflow?

A workflow arranges model calls, tools, and code into a defined structure. You decide the paths; the model does work inside steps. An agent decides its own path. Workflows are more predictable, cheaper, and easier to test, so prefer them when the process is known.

2. Sequential and parallel

3. Routing and branching

4. Loops and reflection

A loop repeats until a condition is met, with a maximum iteration count. Reflection is a loop where the model critiques its own output.

5. Human-in-the-loop and hybrid systems

Insert humans before high-risk decisions (refunds, hiring rejections, deployments). Real systems are hybrids: deterministic code for rules and validation, workflows for structure, LLM steps for language tasks, and an agent only where the path is unknown.

Customer supportRoute → answer or agent → escalate
RecruitingParse → score in parallel → human decides

8. Code: a simple workflow

def support_flow(ticket, llm):
    kind = llm("Classify: billing/tech/other: " + ticket)   # route
    if kind == "billing":
        draft = llm("Draft billing reply: " + ticket)
    else:
        draft = run_agent(ticket)                            # agent step
    for _ in range(2):                                       # bounded reflection
        review = llm("Critique this reply: " + draft)
        if "OK" in review:
            break
        draft = llm("Improve using: " + review + "\n" + draft)
    return request_human_approval(draft)                     # human gate

Code sets the structure; the model handles language; one step is an agent; loops are bounded; a human approves.

9. Common mistakes

  • Agents everywhere, or multi-agent setups you don't need.
  • Uncontrolled loops and no failure path.
  • No human approval on risky steps.
  • Putting rules that must be exact into probabilistic model calls.

Key takeaways

  • Workflows trade flexibility for predictability.
  • Combine patterns; keep autonomy small and bounded.
  • Always define failure paths and approval points.

Multi-Agent Systems

1. Introduction

A multi-agent system uses several agents, each with its own instructions, context, tools and reasoning loop, working toward one goal. A tool is a function; an agent is a decision-maker running its own loop. Split responsibilities when they genuinely separate: for example a researcher that may browse the web and a reviewer that may not, judged by different criteria.

Key point: multiple agents are not automatically better than one well-designed agent. Each extra agent adds communication, cost, latency and failure modes.

2. Single agent vs multi-agent

Single agentMulti-agent
ReasoningOne loopSeveral loops
BehaviorCentralizedSpecialized, distributed
CoordinationSimpleRequired
DebuggingEasierHarder: trace across agents
OverheadLowerHigher: messages, tokens, time
Best whenOne context fits the jobResponsibilities can be separated

A single agent with many tools handles a surprising range of tasks. Try that first.

3. When to use multiple agents

Good reasons
  • Clearly different specializations
  • Independent, parallelizable subtasks
  • Different tools or permissions per role
  • Different evaluation criteria (writer vs reviewer)
  • Context too large for one agent
Poor reasons
  • "One agent per task" for its own sake
  • Roles that overlap
  • Work that is strictly sequential and small
  • A workflow or single agent would do

4. Agent roles

RoleResponsibility
ResearcherFinds and extracts sources

CoderEdits code, runs tests

SupervisorDelegates, tracks, aggregates

A role boundary is meaningful only if it changes instructions, tools, permissions or evaluation. Otherwise merge the roles.

5. Architecture patterns

6. Communication and shared state

Agents communicate through messages, shared state, events and task handoffs. Free-form chat between agents drifts and is hard to test, so use structured messages:

{"from": "researcher", "to": "analyst", "task_id": "t42",
 "status": "done", "artifact": {"sources": ["..."], "notes": "..."},
 "confidence": 0.8}

Shared state (task board, artifacts, intermediate results) needs clear ownership: one writer per field, or conflicts and stale reads appear.

7. Orchestration

The orchestrator delegates, routes, sequences, retries, enforces timeouts, handles failures and aggregates.

Parallel execution helps only for independent tasks; you then need a synchronization point (wait for all, or first N) and an aggregation rule.

8. Failure handling

9. Evaluation

Evaluate each agent alone, the messages between them, and the whole system end to end. Track coordination failures (dropped tasks, duplicated work), cost, latency and reliability. Compare against a single-agent baseline, and keep the simpler system if it performs as well.

12. Code: a simple supervisor

def supervisor(goal, workers, llm):
    plan = llm("Split into tasks as JSON [{worker, task}]: " + goal)
    results = {}
    for t in plan:                                    # could run in parallel
        try:
            results[t["worker"]] = workers[t["worker"]](t["task"], timeout=60)
        except Exception as e:
            results[t["worker"]] = {"error": str(e)}   # failure is data
    if any("error" in r for r in results.values()):
        return escalate(goal, results)
    return llm("Combine into one answer: " + str(results))

The supervisor plans, delegates, catches failures as data, escalates if needed, and aggregates.

Key takeaways

  • Split agents only along real responsibility boundaries.
  • Use structured messages and clear state ownership.
  • Orchestration and failure handling are the hard part.
  • Beat the single-agent baseline before keeping the complexity.

Memory, Context & Knowledge

1. Introduction

An agent is only as capable as the information it can reach at the right moment. Context is what the model sees on this step, memory is what is retained across steps or sessions, and knowledge is external information retrieved when needed. They are related but not the same.

2. Context vs memory vs knowledge

ContextMemoryKnowledge
ScopeOne model callAcross steps or sessionsExternal, shared
Lives inThe promptStore you manageDocs, DBs, APIs
QuestionWhat does the model see now?What should we remember about this user or task?What should we look up?
ExampleInstructions + goal + tool resultsPrefers metric unitsCompany policy PDF

3. The context window

Models read and write tokens, and the window limits input plus output. Even inside the limit, more is not better: irrelevant text dilutes attention, raises cost and latency, and can bury the fact that matters.

4. Context construction

5. Short-term and long-term memory

Short-term (working) memory is conversation history, task state, intermediate results and temporary variables for the current run. Long-term memory persists: user preferences, learned facts, past task outcomes. Store only what will be useful, with a date and source; retrieve when relevant; expire or re-verify old facts.

6. Retrieval

7. RAG

Retrieval-Augmented Generation grounds answers in your own sources. Documents are split into chunks, converted to embeddings (vectors), and stored. At question time the system runs vector search, applies metadata filters, optionally reranks, builds a context and asks the model to answer from it, with citations.

8. RAG vs memory

MemoryRAG
AsksWhat should we remember about this user/interaction?What should we retrieve from a knowledge source?
Written byThe agent, as it learnsCurators or pipelines
ExampleUser works in IST time zoneRefund policy section 4
RiskStale or wrong memoriesWrong or missing chunks

9. Managing context

Prioritise (instructions and the goal always stay), trim old turns, summarise long history, compress tool output, retrieve instead of preloading, and filter by relevance. Putting a whole database in the prompt is a poor architecture: slow, costly, insecure and less accurate.

10. Memory failures

13. Code: building context

def build_context(goal, user_id, budget=3000):
    parts = [SYSTEM_PROMPT, "Goal: " + goal]
    prefs = memory.search(user_id, goal, top=2)          # long-term memory
    docs = kb.search(goal, top=8)                         # retrieval
    docs = [d for d in docs if d.score > 0.75][:3]        # relevance filter
    parts += ["Memory: " + m.text for m in prefs]
    parts += ["Source[" + d.id + "]: " + d.text for d in docs]
    return trim(parts, max_tokens=budget)                 # prioritise + trim

Memory and knowledge are fetched separately, filtered, labelled with sources, and trimmed to a budget.

14. Common mistakes

  • Storing or retrieving everything
  • No relevance filtering
  • Mixing memory and knowledge
  • Stale memories left unchecked
  • Context overload
  • No privacy boundaries

Key takeaways

  • Context is per call; memory persists; knowledge is retrieved.
  • Relevant beats large.
  • RAG answers from sources; memory personalises.
  • Memory needs expiry, correction and privacy rules.

Reliable & Trustworthy AI Agents

1. Why reliability matters

Agents are non-deterministic and act on real systems. Expect tool failures, hallucinations, wrong decisions, unexpected loops and outages in external services. Reliable engineering assumes these will happen and limits the damage.

2. Guardrails

Guardrails are checks at boundaries: input (reject or sanitise), output (policy and format), tool (arguments and permissions) and policy constraints (rules the agent may never break).

3. Permissions

Apply least privilege: give each agent only the tools and data it needs, prefer read-only, and treat irreversible actions (delete, pay, send) as a separate, gated class.

ActionClassPolicy
Read a fileRead, reversibleAllow
Edit a draftWrite, reversibleAllow with logging
Send an emailWrite, externalApproval or confirmation
Delete data / payIrreversibleHuman approval

4. Human-in-the-loop

Require approval for financial actions, deleting data, sensitive communications, production changes and high-impact decisions. Use a confidence or risk threshold so people review what matters instead of everything.

5. Validation

6. Hallucinations

In agents, hallucination includes fabricated facts, misread tool results, unsupported conclusions and false confidence. Mitigate with retrieval, verifying claims through tools, structured outputs, source checks, evaluation and human review.

7. Tool safety

Tools are powerful because they act, and dangerous for the same reason. Validate inputs, sandbox code execution, apply rate limits, require confirmation for destructive operations, and never let model text become unchecked shell or SQL.

8. Stop conditions

9. Retries and recovery

ErrorAction
Timeout, rate limit, 5xxRetry with exponential backoff, capped
Invalid argumentsReturn error to the model once
Permission denied, not foundDo not retry; fallback or escalate
Tool unavailableAlternate tool, or partial result

Never retry everything; blind retries multiply cost and side effects.

10. Evaluation

DimensionQuestion
Task successDid it achieve the goal?
Tool correctnessRight tools chosen?
Argument correctnessValid parameters?

SafetyAny constraint violated?
ReliabilityConsistent across scenarios?

11. Observability

12. Testing agents

Use unit tests for tools, integration tests for the loop, scenario tests for realistic tasks, adversarial tests (prompt injection, bad inputs), regression tests when you change prompts or models, and evaluation datasets. Unlike deterministic code, run each case several times and measure pass rates.

13. Production checklist

  • Permissions least-privilege
  • Validation on every tool call
  • Step, time and cost limits
  • Retries with backoff
  • Human approval for risky actions
  • Logging, tracing, monitoring
  • Evaluation suite and regression tests
  • Rollback or fallback path

14. Practical example: production-aware coding agent

15. Code: safe tool execution

ALLOWED = {"analyst": {"read_file", "run_tests"}, "editor": {"read_file", "write_file"}}
RISKY = {"write_file", "delete_file"}

def safe_execute(role, call, step, max_steps=8):
    if step >= max_steps: return {"error": "step limit"}
    if call["name"] not in ALLOWED[role]: return {"error": "not permitted"}
    if not valid_args(call): return {"error": "invalid arguments"}
    if call["name"] in RISKY and not human_approves(call):
        return {"error": "rejected by human"}
    try: return {"result": TOOLS[call["name"]](**call["args"])}
    except TimeoutError: return {"error": "timeout", "retryable": True}

Order matters: limits, permissions, validation, approval, then execution with error handling.

16. Common mistakes

  • Trusting model output blindly
  • Unrestricted tools; no step limits
  • No logging or evaluation
  • Retrying everything
  • No human escalation path
  • Storing sensitive data unnecessarily

Key takeaways

  • Assume failure; bound the damage.
  • Least privilege plus validation plus approval for risk.
  • Measure and observe; you cannot fix what you cannot see.

11. Code skeleton

def research(question, agents, tools):
    plan = agents.planner(question)
    evidence = []
    for q in plan["queries"][:MAX_QUERIES]:
        hits = safe_execute("researcher", {"name": "search", "args": {"q": q}}, 0)
        evidence += validate_sources(hits)
    draft = agents.synthesizer(question, evidence)
    for _ in range(2):                               # bounded improvement loop
        review = agents.reviewer(draft, evidence)
        if review["approved"]: break
        draft = agents.synthesizer(question, evidence, feedback=review["issues"])
    return request_human_approval(draft)
