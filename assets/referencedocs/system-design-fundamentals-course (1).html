Introduction to System Design

1.1 What is system design?

System design is deciding which components a system has, what each is responsible for, how they communicate, where data lives, and how the whole behaves under load and failure. Designing a component (a function, a class, one endpoint) asks "is this code correct?". Designing a system asks "what happens when a million people call it, a disk dies, and a dependency slows down at once?"

Scale changes decisions. A notes app for ten users can keep everything in one process and one database. The same app for ten million users needs answers to questions that never came up before: where do requests go, what if a machine fails, how is data kept safe and fast?

1.2 Functional vs non-functional requirements

Functional requirements say what the system does ("users can post a photo"). Non-functional requirements say how well it must do it, and they drive architecture far more than features do.

QualityQuestion it answers
AvailabilityWhat fraction of time can users use it?
ScalabilityCan it handle 10× the load by adding resources?
Latency / throughputHow long does one request take / how many per second?
Reliability / durabilityDoes it behave correctly / is stored data never lost?
ConsistencyDoes every reader see the latest write?
Security, maintainability, costIs it protected, changeable, affordable?
Same feature, different architecture. "Show account balance" for a bank demands strong consistency and durability; for a social "likes" counter, slightly stale numbers are fine and availability and speed matter more. Same functional requirement, very different designs.

1.3 Scaling

Vertical scaling means a bigger machine. It is simple, but it has a hard ceiling, gets expensive quickly, and leaves a single point of failure. Horizontal scaling means more machines sharing the load. It scales further and tolerates failures, but only works cleanly if servers are stateless: any server can handle any request because session and user data live in shared storage, not in one server's memory.

1.4 Architecture evolution

Real systems grow one problem at a time. Step through the stages and read what each new component solves.

1.5 Monolith vs modular monolith vs microservices

1.6 How to approach a design problem

  1. Clarify requirements (functional and non-functional)
  2. Estimate scale (users, requests/sec, storage)
  3. Identify major components
  4. Define APIs and data flow
  5. Choose storage
  6. Consider caching
  7. Consider asynchronous processing
  8. Find bottlenecks
  9. Analyse failure modes
  10. Discuss trade-offs
# Illustrative pseudocode, not production code: a stateless endpoint
def get_profile(request):
    user_id = verify_token(request.token)     # identity comes from the request
    return db.read("profiles", user_id)       # state lives in shared storage

Key takeaways

  • System design is about behavior at scale and under failure.
  • Non-functional requirements shape architecture.
  • Vertical scaling is simple but capped; horizontal scaling needs stateless servers.
  • Add components only to solve an observed bottleneck.
  • No architecture style is universally superior.

Practical exercise

A recipe-sharing app grows from 500 to 500,000 users. Choose an architecture stage (from 1.4) and a code structure (from 1.5), and justify both against one non-functional requirement.

Distributed System Fundamentals

2.1 What is a distributed system?

A distributed system is a set of independent machines (nodes) that cooperate over a network to do work and share state, while presenting themselves to users as one system. Search engines, online banking, video streaming, ride-hailing and multiplayer games all work this way. Even a web app with an application server and a separate database is already distributed.

Systems become distributed for three reasons: capacity (one machine cannot hold or serve everything), fault tolerance (one machine dying should not end the service) and proximity (data closer to users is faster). The price is that you swap function calls, which almost always succeed, for network calls, which can be slow, lost or answered by a machine that has crashed.

Single-process appDistributed system
CommunicationFunction call in memoryMessages over a network
FailureEverything fails togetherParts fail independently (partial failure)
StateOne memory, one truthCopies on several machines that may disagree
TimeOne clockMany clocks that drift apart

The client only knows one entry point. The nodes run the same code and can be added or removed. Storage is where data survives, which is why it becomes the hardest part to scale and protect (Module 4).

2.2 Why distributed systems are difficult

"Distributed systems are hard" is not useful. Here is what specifically goes wrong, using a payment request as the running example.

  • Latency: a call that took 1 ms in memory takes 1 to 100+ ms over a network, and occasionally seconds. Calls that were cheap in one process become expensive when chained across services.
  • Lost messages / packet loss: the "charge card" request never arrives. The client waits, and cannot know whether the card was charged.
  • Lost replies: the payment succeeded but the confirmation was dropped. The client sees a timeout for a payment that actually happened.
  • Duplicated messages: the client retries after the timeout, so the server receives the same charge twice unless it deduplicates.
  • Delayed and reordered messages: "cancel order" can arrive before "create order".
  • Machine crashes: a server dies halfway through a multi-step operation, leaving it half done.
  • Partial failure: the payment service is up but its database is not; the order service works but cannot complete anything.
  • Network partitions: two groups of healthy machines cannot reach each other and each may think the other is dead.
  • Race conditions: two servers read balance 100 at once and both approve a 80 purchase.
  • Clock differences: two machines stamp the same moment with different times, so "which happened first?" has no trustworthy answer.
  • Inconsistent state: replicas hold different values for the same record at the same instant.
Core problem: a timeout tells you only that you did not get an answer. The other machine may have crashed, be slow, or have succeeded with a lost reply. Designs must cope with that uncertainty, usually with timeouts, retries and idempotent operations that are safe to repeat.
# Pseudocode: illustrative, not tied to a specific SDK
def charge(order_id, amount):
    for attempt in range(3):
        try:
            return payments.charge(order_id, amount, idempotency_key=order_id, timeout=2.0)
        except Timeout:
            sleep(backoff(attempt))     # unknown outcome: retry is safe only because of the key
    raise GiveUp("outcome unknown; reconcile later")

2.3 Nodes, services, networks and failure domains

These terms are often mixed up. A process is a running program. An instance is one running copy of a program or service (for example one of five copies of the checkout service). A node is a machine or virtual machine that runs processes. A service is a capability (checkout, search) provided by one or more instances. A network boundary is any place where communication crosses from one machine or network to another; every boundary crossing can be slow, lost or blocked.

A failure domain is a group of components that tend to fail together: a single process, a machine, a rack, a power feed, an availability zone (an isolated data-centre location within a cloud region), or an entire region. Redundancy only helps if copies sit in different failure domains. Three replicas in one rack are one failure away from none.

Nodes fail independently, and there is no shared clock or memory, so no node can assume it sees the same state as the others at the same moment. Information takes time to travel, so every node works with a slightly old picture of the rest of the system.

2.4 Consistency and replication

Replication keeps copies of data on several nodes. It exists for durability (a copy survives a crash), availability (another copy can serve) and read capacity. In primary/replica replication all writes go to the primary, which forwards changes to replicas.

Follow one write. (1) A client changes a user's display name. (2) The primary stores it and writes it to its log. (3) The primary sends the change to replicas. (4) In synchronous replication the primary waits for replicas to confirm before answering the client: no acknowledged write is lost if the primary dies, but every write pays the slowest replica's latency and a dead replica can block writes. In asynchronous replication it answers immediately and replicates afterwards: writes are fast, but replicas lag. (5) If another client reads from a replica during that replication lag, it gets the old name: a stale read.

  • Strong consistency: once a write is acknowledged, every later read sees it (or something newer).
  • Eventual consistency: if writes stop, all replicas converge; reads may be stale until then.
  • Read-after-write consistency: you always see your own writes, even if others may not yet. A common fix is reading your own recent writes from the primary.

Failover interacts with this: if the primary dies while replicas lag, promoting a replica can lose the writes it never received (see 2.5).

2.5 Failover and fault tolerance

A single point of failure is any component whose loss stops the system. Redundancy (spare copies) removes it. Failover is moving work from a failed component to a spare. For a database it looks like this: health checks or heartbeats notice the primary is not responding; a replica is promoted to primary; clients are redirected; the old primary later recovers and rejoins as a replica.

Failover is never instant, so there is a window with no primary and writes fail. If replication was asynchronous, the promoted replica may be missing the last writes, which is temporary inconsistency or data loss. A health check that is too sensitive can also trigger unnecessary failovers.

2.6 Leader election

Many systems choose one leader to make decisions: order writes, hand out work, hold a lock. One decision-maker avoids conflicting decisions. Followers monitor it through heartbeats, small periodic messages. When followers stop hearing them for a timeout, they suspect the leader failed and hold an election: a candidate asks the others for votes, and each node votes once per term (an election round). A candidate with a majority wins.

The danger is split-brain: a partition makes both sides believe the leader is gone, so two nodes both act as leader and accept conflicting writes. Requiring a majority of votes prevents this, because two disjoint groups cannot both hold a majority, and a returning old leader steps down when it sees a higher term.

# Pseudocode: illustrative, not tied to a specific SDK, not a full election algorithm
on election_timeout():
    term += 1; votes = 1                      # vote for self
    for peer in peers: send(peer, RequestVote(term))
on vote_granted():
    votes += 1
    if votes > cluster_size // 2: become_leader(); start_heartbeats()

2.7 CAP theorem

CAP is often summarised as "pick two of three", which is misleading. Its definitions are specific. Consistency here means linearizability: every read sees the latest completed write, as if there were one copy. Availability means every request to a working node receives a non-error response. A network partition means the network splits so some nodes cannot reach others, though every node is still running.

Partitions are a property of networks, not a feature you can decline, so partition tolerance is not optional in a distributed system. The theorem (Gilbert and Lynch's formal version) says that during a partition a replicated system cannot be both consistent and available. Faced with a request it cannot safely answer, it must either refuse (consistency-first, CP) or answer with possibly stale or divergent data (availability-first, AP). When there is no partition it can offer both; real designs then trade latency against consistency, which CAP does not describe.

Choose per feature. A ledger balance should refuse rather than show wrong money. A product catalogue or "likes" count should keep answering.

2.8 Consensus

Consensus is getting several nodes to agree on one value (who is leader, which write is next in the log) even though some nodes may crash and messages may be lost. It is not the same as ordinary replication, which just copies data; consensus decides what to copy and when it counts as committed.

The common pattern is leader-based with a quorum. In Raft (a consensus algorithm designed to be understandable), clients send changes to the leader, which appends the change to its log and replicates it to followers. Once a majority (more than half of all nodes, counting the leader) has stored it, the entry is committed and applied. With n nodes, the majority is floor(n/2)+1, and the cluster tolerates floor((n-1)/2) failures: 3 nodes tolerate 1, 5 tolerate 2. Any two majorities overlap in at least one node, which is what stops two conflicting decisions from both being committed.

# Pseudocode: illustrative, not tied to a specific SDK
def majority(n): return n // 2 + 1
def can_commit(n, failed): return (n - failed) >= majority(n)

2.9 Time, clocks and ordering

Each machine has its own clock, and clocks drift; synchronisation protocols such as NTP reduce the error but do not remove it. Clock skew is the difference between two clocks. If you order events by timestamp, skew can put an effect before its cause. Imagine Node A records event A1 (an order is created) and sends a message. Node B receives it and records B1 (the order is shipped). If B's clock runs behind, B1 gets an earlier timestamp than A1, even though A1 clearly caused B1. A smaller timestamp does not prove that an event came first, or caused another.

Logical clocks avoid wall time. In Lamport's scheme each node keeps a counter that increases on every local event; each message carries the sender's counter, and the receiver sets its counter to one more than the larger of its own and the received value. This guarantees that if one event caused another, its number is smaller. It does not work backwards: a smaller number does not prove causality, since unrelated events can also be ordered arbitrarily.

Key takeaways

  • Distributed systems have independent, partial failures over unreliable networks.
  • A timeout means "no answer", not "it did not happen"; design for retries and idempotency.
  • Redundancy helps only across separate failure domains.
  • Synchronous replication trades latency for safety; asynchronous trades safety for speed and causes stale reads.
  • Failover has a gap and may lose unreplicated writes.
  • Leaders simplify decisions; majority voting and terms prevent split-brain.
  • CAP's trade-off applies during a partition: refuse or risk stale data.
  • Consensus needs a majority; n nodes tolerate floor((n-1)/2) failures.
  • Timestamps from different clocks can mislead; logical clocks track causality.

Practical exercise

An order service runs in two zones with a primary database in zone 1 and an asynchronous replica in zone 2. Zone 1 loses power for two minutes. Write down: (1) what failed, (2) what stays available, (3) what data may be stale or missing after promoting the replica, (4) which recovery mechanism (idempotent retries, reconciliation, synchronous replication for payments) you would add, and why.

Communication in Distributed Systems

3.1 Request/response fundamentals

A client sends a request; a server does work and returns a response. Two numbers describe the exchange: latency (how long one request takes) and throughput (how many requests per second the system completes). Every hop crosses a network boundary, and each crossing adds delay and a chance of failure. A timeout is how long the caller waits before giving up; it is a decision, not a fact about the other side.

3.2 API communication

An API contract states what a client may send and what it gets back: the endpoint (resource address), method, parameters, payload and status codes. REST models resources over HTTP (GET reads, POST creates, PUT/DELETE change). RPC exposes actions as remote function calls. A method is idempotent if repeating it has the same effect as doing it once (GET, PUT, DELETE should be; a bare POST is not), which is what makes retries safe. Versioning (for example /v2/) lets you change a contract without breaking existing clients.

3.3 Synchronous communication

In synchronous calls the caller blocks until it gets an answer. That is simple to reason about, but calls form a dependency chain: latency adds up along the chain and a slow or failed leaf slows or fails everything above it, while every caller holds threads and connections open while waiting.

3.4 Asynchronous communication

With asynchronous communication the API puts a message in a queue and answers immediately; a worker (consumer) handles it later. The queue buffers bursts and decouples producer from consumer: they can scale, fail and deploy independently. The cost: the result is not ready when the response returns, so you need status polling, callbacks or notifications, and you must handle duplicate or out-of-order work.

3.5 Message queues

A producer enqueues messages; a consumer takes one, processes it and sends an acknowledgement (ack). Without an ack the message returns for retry. Messages that keep failing move to a dead-letter queue (DLQ) for inspection. When consumers fall behind, consumer lag (queue depth) grows. Because a message can be delivered twice (a consumer may crash after working but before acking), consumers should be idempotent.

# Pseudocode: illustrative, not tied to a specific SDK
def consume(queue):
    msg = queue.receive()
    try:
        handle(msg)                  # must be safe to run twice
        queue.ack(msg)
    except Exception:
        if msg.attempts >= 3: dead_letter_queue.send(msg)
        else: queue.release(msg)     # will be redelivered

3.6 Publish/subscribe

In pub/sub a publisher sends an event to a topic; every subscriber gets its own copy. This fan-out means the publisher does not know who listens, so adding a new consumer needs no change to it. Compare with a queue, where each message is handled by one consumer.

3.7 Load balancing

A load balancer spreads requests over servers so none is overloaded and a failed server is bypassed. Round robin gives each server the next turn; it is fair only when requests and servers are alike. Least connections prefers the server with the fewest in-flight requests, which helps when some servers are slower. Health checks probe servers periodically, and a server that fails them is removed until it recovers.

3.8 Timeouts, retries and backoff

Without a timeout a caller can wait forever. A retry recovers from brief failures, but naive retries hurt: if a dependency is struggling and every client retries at once, the extra load keeps it down, a retry storm. Exponential backoff waits longer after each failure (1s, 2s, 4s); jitter adds randomness so clients do not retry in lockstep. Retry only idempotent operations, with a limit.

# Pseudocode: illustrative, not tied to a specific SDK
for attempt in range(max_retries + 1):
    if call(timeout=1.0).ok: return
    sleep(random() * min(cap, base * 2 ** attempt))   # exponential backoff with full jitter

3.9 Rate limiting

Rate limiting protects a service from abuse and overload and shares capacity fairly. In a token bucket the bucket holds up to a capacity of tokens that refill at a steady rate; each request spends a token. If tokens remain the request is allowed; if not it is rejected (HTTP 429) or throttled (delayed). The bucket allows short bursts up to its capacity but limits the long-run rate.

Key takeaways

  • A request crosses several network boundaries; latency is the sum of hops.
  • A timeout means no answer, not failure of the operation.
  • Idempotent operations make retries safe.
  • Synchronous chains propagate latency and failure upward.
  • Queues decouple, buffer and smooth load, but need acks, retries, a DLQ and idempotent consumers.
  • Queue = one consumer per message; pub/sub = every subscriber gets a copy.
  • Least connections helps with uneven servers; health checks remove dead ones.
  • Retries need limits, backoff and jitter to avoid retry storms.
  • Token buckets allow bursts but cap the average rate.

Practical exercise

A photo app must, on upload, save the file, generate three thumbnails, and notify followers. Decide which steps stay synchronous and which become asynchronous. For each queue say what happens if the worker crashes mid-task, how you avoid duplicates, and what the user sees while processing.

Storage & Data Management

4.1 Choosing storage

Choose storage by how the data is accessed, not by fashion. Relational databases suit structured, related data and transactions. Document stores hold flexible, self-contained records. Key-value stores give very fast lookup by key. Wide-column stores handle massive write volumes spread across many machines. Graph databases make relationship traversal cheap. Object storage holds files and blobs. A cache keeps hot copies of data in fast memory. Real systems combine several.

4.2 Relational databases

Data lives in tables of rows. A primary key identifies a row; a foreign key points to a row elsewhere, forming relationships. Normalisation stores each fact once and links to it. A transaction groups changes so they all happen or none do (ACID: atomicity, consistency, isolation, durability). Indexes speed up lookups (4.4).

4.3 NoSQL

"NoSQL" covers several models that trade some relational features for scale or flexibility. Pick by access pattern.

4.4 Indexing

Without an index the database does a full scan, reading rows until it finds matches: cost grows with table size. An index is a separate sorted structure (often a B-tree) that jumps to matching rows in a few steps. The price: extra storage, and every insert or update must also update the index, so write overhead rises. Index the columns you filter or join on, not everything.

-- Illustrative SQL
CREATE INDEX idx_orders_user ON orders(user_id);
SELECT * FROM orders WHERE user_id = 9;   -- can now use the index

4.5 Replication

Storage replication is the mechanism from Module 2: writes go to a primary and flow to replicas, which add read capacity and durability, at the cost of replication lag and stale reads. See the consistency and failover simulators in Module 2 for interactive versions.

4.6 Sharding

Sharding (horizontal partitioning) splits data across machines so no machine holds it all. A shard key decides which shard owns a record. A good key spreads data and traffic evenly and matches common queries. A poor key creates a hot partition (one shard overloaded) or forces queries to touch every shard. Adding shards means rebalancing, moving data, which is expensive with naive hashing (see 4.7).

4.7 Consistent hashing

With shard = hash(key) mod N, changing N remaps most keys. Consistent hashing places nodes and keys on a ring; each key belongs to the first node clockwise from it. Adding or removing a node only moves the keys next to it, roughly 1/N of all keys.

4.8 Caching

A cache hit returns data from fast memory; a miss goes to the database. In cache-aside the application checks the cache, on a miss reads the database and fills the cache. A TTL (time to live) expires entries so data does not stay stale forever; invalidation removes entries when the source changes. Longer TTL means higher hit rate but staler data.

Miss path
# Pseudocode: illustrative cache-aside
def get(key):
    v = cache.get(key)
    if v is not None: return v          # hit
    v = db.read(key)                    # miss
    cache.set(key, v, ttl=60)
    return v

4.9 Durability and recovery

Durability means acknowledged data is not lost. Replicas protect against a machine failing; backups protect against mistakes and corruption that replication would copy everywhere. Recovery is judged by RPO (how much data you can lose, measured in time) and RTO (how long recovery may take). Durability and availability differ: data can be safe but unreachable. Disaster recovery adds copies in another region.

Key takeaways

  • Choose storage by access pattern and trade-offs, and combine several.
  • Relational: relationships, constraints and transactions.
  • NoSQL models trade features for scale or flexibility.
  • Indexes speed reads but cost writes and storage.
  • Replication adds read capacity and durability, plus lag.
  • A bad shard key causes hot partitions.
  • Consistent hashing moves only about 1/N of keys when nodes change.
  • Cache-aside plus TTL trades freshness for speed.
  • Replicas do not replace backups; know your RPO and RTO.

Practical exercise

Design storage for a ride-sharing app: trips, driver locations updated every 5 seconds, receipts as PDFs, and a "drivers near me" query. Choose a store for each, the shard key for trips and why, what you cache and the TTL, and your backup and recovery targets.

Security in System Design

5.1 Security principles

The CIA triad: confidentiality (only the right people read data), integrity (data is not changed improperly), availability (authorised users can use the system). Least privilege gives each user and service only the access it needs. Defense in depth stacks independent protections so one failure is not fatal.

5.2 Authentication

Authentication proves who you are using credentials (password, key, one-time code). After success the system issues a session (server-side state) or token (a signed value the client presents on each request) so the user does not log in every time. Tokens should expire and be sent only over encrypted connections.

5.3 Authorization

Authentication answers "who are you?"; authorization answers "what may you do?". Permissions are often grouped into roles. A valid login does not imply access: a request can be authenticated but forbidden (HTTP 403), while an unauthenticated one is 401.

5.4 Encryption

Encryption in transit protects data moving over a network (TLS); encryption at rest protects stored data (disk, database, backups). Symmetric encryption uses one shared key and is fast. Asymmetric encryption uses a public/private key pair. TLS conceptually: the server proves its identity with a certificate, the two sides use asymmetric cryptography to agree on a shared key, then encrypt traffic symmetrically.

5.5 Secrets

Secrets (API keys, database passwords, signing keys) must not be hardcoded or committed to source control, because code is copied widely. Store them in a secret manager, give each service access only to what it needs, and rotate them so a leaked secret has a short life.

5.6 Threats and trust boundaries

A trust boundary is where data passes between zones with different trust levels: internet to gateway, gateway to application, application to database. Everything crossing must be authenticated, validated and limited. Common threats, conceptually: credential theft (stolen passwords), unauthorised access (missing permission checks), injection (untrusted input treated as commands), replay (resending a captured valid request), abuse and denial of service (overwhelming capacity).

5.7 Defense in depth

No single control is enough. Layers stop different threats at different points, and if one fails or is misconfigured the next still helps. Switch layers off, then send a threat and see where it is stopped.

Security by design: decide boundaries, identities and data sensitivity at architecture time; retrofitting is costly and leaves gaps.

Key takeaways

  • Think in confidentiality, integrity and availability.
  • Least privilege limits damage from mistakes and theft.
  • Authentication proves identity; authorization decides access.
  • 401 means not authenticated; 403 means authenticated but not allowed.
  • Encrypt in transit (TLS) and at rest.
  • Never hardcode secrets; use a manager and rotate.
  • Identify trust boundaries and validate input at each one.
  • Defense in depth: layers cover each other's gaps.

Practical exercise

Draw a web app with browser, CDN, API gateway, order service, payment service and database. Mark every trust boundary. For each, state what is authenticated, what is authorised, what is encrypted, where secrets are stored, and which layer would stop a stolen user token being used to read another user's orders.

Trade-offs & Real-World Design Principles

6.1 No perfect architecture

Every design trades simplicity, scalability, reliability, consistency, latency, cost and operational complexity against each other. The right answer depends on requirements. Choose a change below to see its qualitative effects.

6.2 Latency vs throughput

Latency is the time for one request; throughput is requests completed per second. As load approaches capacity, requests queue and latency rises sharply while throughput stops growing (saturation).

6.3 Availability vs consistency

A user changes their email while two data centres cannot talk to each other. What should the system do?

6.4 Cost vs reliability

Redundancy removes single points of failure but multiplies infrastructure, monitoring and on-call work. Spend where an outage is costly.

Single instance
1 app server, 1 database. Cheap, simple. Any failure means downtime; maintenance needs downtime too.
Redundant
Several app servers behind a load balancer, database replicas, automated failover, multiple zones. Survives failures; several times the infrastructure plus failover testing, monitoring and more complex deployments.

6.5 Complexity

Premature microservices and unneeded infrastructure add network calls, deployment pipelines, versioned contracts and harder debugging before they are needed. Split when independent scaling or independent teams justify it.

6.6 Bottleneck analysis

Measure, find the bottleneck (the layer that saturates first), change that, measure again. Adding capacity elsewhere changes nothing. After you fix one bottleneck, the next appears.

6.7 Failure modes

Common failure modes: single points of failure, overload, dependency failure, database bottleneck and cascading failure, where one failing component exhausts the resources of its callers. Timeouts, bulkheads and circuit breakers (stop calling a failing dependency for a while and return a fallback) contain the damage.

6.8 Backpressure

Backpressure is a system protecting itself when downstream capacity is exceeded: bound the queue, reject or slow the producer, or shed load, instead of buffering without limit and running out of memory or serving responses too late to matter.

6.9 Observability

Logs record events, metrics are numbers over time (rate, errors, latency), traces follow one request across services. Health checks tell load balancers and orchestrators whether an instance can serve.

Key takeaways

  • Every design is a trade-off; requirements decide.
  • Near saturation, latency rises sharply and throughput plateaus.
  • Under a partition choose consistency or availability per feature.
  • Redundancy costs money and operational effort.
  • Do not adopt microservices or infrastructure before they are needed.
  • Fix the measured bottleneck, then measure again.
  • Timeouts and circuit breakers stop cascades.
  • Backpressure bounds queues instead of hiding overload.
  • Logs, metrics and traces answer different questions.

Practical exercise

A checkout page slows from 300 ms to 6 s during a sale. Metrics: app CPU 35%, cache hit rate 92%, database CPU 98%, queue empty. Identify the bottleneck, propose one change, predict what becomes the next bottleneck, and say which metric you would check to confirm.

System Design Practice & Wrap-Up

7.1 Start with requirements

Clarify before drawing. Functional: what the system does. Non-functional: scale, latency, availability, consistency, durability. Assumptions are guesses you state aloud; constraints are given limits (budget, team, deadline). Our running example is a URL shortener: create a short link, redirect to the original, optionally see click counts. Assume 100 million new links per month, reads 100 times more than writes, redirects under 100 ms, links must not be lost.

7.2 Estimate scale

Rough numbers guide choices. Requests/sec = daily requests / 86,400; peak is often 2-5× average; storage/day = writes × record size; bandwidth = requests/sec × payload size. These are estimates for reasoning, not measurements.

7.3 Define APIs

# Illustrative API sketch
POST /v1/links        body: {"url": "https://example.com/a/very/long/path"}  → 201 {"code": "aZ3k9"}
GET  /{code}          → 302 Location: original URL          (idempotent, cacheable)
GET  /v1/links/{code}/stats → 200 {"clicks": 1234}          (auth required)

7.4 High-level architecture: the playground

Build the system yourself. Start with one app server, put traffic on it, and add components only when the observations tell you why. 90% of traffic is reads; illustrative capacities: app server 200 req/s, database 400 req/s.

7.5 Worked scenario: designing the URL shortener

Design is iterative: each answer exposes new questions. Step through the same scenario.

Interview tip: state assumptions, design the simple version first, then say which bottleneck you would fix next and why.

Key takeaways

  • Clarify requirements and state assumptions before designing.
  • Estimate requests/sec, storage and bandwidth to size the design.
  • Define the API and its idempotency early.
  • Start simple; add caches, replicas, queues only for a reason.
  • Read-heavy systems benefit from caching and replicas.
  • Slow or bursty work belongs behind a queue.
  • Design for failure: remove single points of failure and set timeouts.
  • Secure each boundary and discuss trade-offs explicitly.

Practical exercise

Design a notification system that sends email and push messages for 5 million users. Write requirements and assumptions, estimate peak requests/sec, sketch the API, name components, choose storage, place queues and caches, list two failure modes with mitigations, one security concern, and one trade-off you accepted.
